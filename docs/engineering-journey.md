# Phase 2 — RAG + Retrieval Foundations

**Days 9–15**

The second phase focused on understanding retrieval behavior experimentally.

### Day 9 — Local RAG

Built a local RAG pipeline using FAISS.

```text
documents
   ↓
chunk
   ↓
embed
   ↓
FAISS
   ↓
retrieve
   ↓
generate
```

### Day 11 — Chunking Strategy Evaluation

Four strategies were compared.

| Strategy               | Chunks |  Avg Size | Accuracy |
| ---------------------- | -----: | --------: | -------: |
| Fixed 500, no overlap  |     95 | 382 chars |      8/9 |
| Fixed 500, overlap 100 |    100 | 396 chars |      8/9 |
| Small 200, overlap 50  |    268 | 141 chars |      8/9 |
| Heading-aware Markdown |     25 | 305 chars |      2/9 |

**Selected:** Fixed 500, no overlap.

The strategy achieved the same measured accuracy as the alternatives tested while producing substantially fewer chunks than the small-chunk configuration.

### Day 12 — Semantic vs Keyword Search

| Method   |       Result |
| -------- | -----------: |
| Keyword  |  15/20 (75%) |
| Semantic | 20/20 (100%) |

The observed keyword failures were primarily vocabulary mismatches between the user query and document terminology.

### Day 13 — Retrieval Pipeline

Implemented:

```text
retrieve → rank → return
```

### Day 14 — Citation Integrity

Built a citation pipeline where the source list is constructed from retrieval results rather than generated by the LLM.

This established the architectural separation later used by the Knowledge Agent.

### Day 15 — Retrieval Configuration

Compared:

| Configuration               | Score |
| --------------------------- | ----: |
| Similarity k=3, 500 tokens  | 25/30 |
| MMR k=5, 500 tokens         | 28/30 |
| Similarity k=5, 1000 tokens | 29/30 |

**Selected:** Similarity `k=5` with `max_output_tokens=1000`.

## Day 18 — Retrieval Benchmark

A 31-question hard benchmark was used to compare retrieval approaches.

### Hard Benchmark

| Method            | Top-1 | Top-5 |
| ----------------- | ----: | ----: |
| Keyword           |   84% |   94% |

| Hybrid            |  100% |  100% |

The major finding was that keyword retrieval degraded under vocabulary mismatch, while vector and hybrid approaches remained strong in this benchmark.

## Day 22 — Evaluation Framework

The evaluation framework was expanded to measure:

* Retrieval hit rate
* Source precision
* Answer groundedness
* Citation accuracy
* Refusal accuracy
* Overall pass rate

The canonical evaluation run achieved:

| Metric                | Canonical Result |
| --------------------- | ---------------: |
| Retrieval Hit Rate @5 |              98% |
| Retrieval Hit Rate @3 |              98% |
| Source Precision      |              48% |
| Average Groundedness  |       2.29 / 3.0 |
| Fully Grounded        |              76% |
| Citation Accuracy     |             100% |
| Refusal Accuracy      |              80% |
| Overall Pass Rate     |              94% |

The first evaluation run exposed a groundedness-judge calibration issue. The judge was comparing against an empty reference rather than the retrieved context. The evaluation was corrected before the canonical run.

Three important failure patterns were identified:

1. Cross-domain retrieval misses
2. Short-query over-refusal
3. Topical inference hallucination

→ See [Knowledge Agent Evaluation](../evaluations/knowledge_agent_report_2nd_run.md)

## Day 23 — Prompt Injection Testing

Eight attack scenarios were tested.

### Baseline

**4/8 blocked — 50%**

### Defensive Prompt

**8/8 blocked — 100%**

The test suite covered:

* Direct injection
* Indirect injection

The defensive prompt introduced controls around:

* Instruction override resistance

The 100% result applies to this specific eight-attack test suite; it is not a universal security guarantee.

# Phase 4 — LangGraph Agent Engineering

**Days 28–40**

This phase moved from retrieval-focused systems to stateful, tool-using agents.

## Day 28 — First LangGraph

Built a three-route classification graph using `StateGraph`.

```text
request
   ↓
classify
   ↓
route
   ↓
response
```

## Day 29 — State Schema

Designed `AgentState` with:

* Typed fields
* `add_messages` reducer
* `operator.add` accumulators
* Multi-turn state accumulation

## Day 30 — Conditional Routing

Expanded the system to six routes:

* `shipment_delay`
* `refund_request`
* `product_defect`
* `account_issue`
* `general`
* fallback

## Day 31 — Tool Design

Implemented five typed read tools:

* `get_customer`
* `get_order`
* `get_shipment`
* `check_inventory`
* `get_refund_policy`

Tools use typed input/output schemas and deterministic validation.

## Day 32 — Tool-Calling Agent

Integrated:

* LangGraph `ToolNode`
* Azure Chat model
* Managed identity authentication
* Automatic tool selection

The agent could determine when multiple tools were required to answer an operational question.

## Day 33 — Full Agent Graph

The architecture evolved into:

```text
request_validator
        ↓
clarification_node
        ↓
       END
        ↑
        │
    agent_node
        ↓
    read_tools
        ↓
    agent_node
        ↓
   approve_node
        ↓
    write_guard
        ↓
       END
```

Read actions could loop through tools.

Write actions were separated into an approval-controlled path.

## Day 34 — State Persistence

Added `InMemorySaver`.

Verified:

* State persistence across turns
* Conversation accumulation
* Tool-call accumulation
* Customer context retention
* Thread isolation

## Day 35 — Database Integration

Migrated operational tools to SQLAlchemy ORM.

Models included:

* Customer
* Order
* Shipment
* Inventory
* AuditLog

Tool calls were logged with session context and timestamps.

## Day 36 — Human Approval

Implemented LangGraph `interrupt()` for write actions.

```text
write proposal
      ↓
human approval
   ↙       ↘
reject    approve
  ↓          ↓
audit    idempotency
             ↓
          execute
```

Rejected actions are logged and not executed.

Approved actions receive an idempotency key.

## Day 37 — Failure Handling

Tested six failure modes:

1. Tool timeout
2. Database connection error
3. Invalid tool arguments
4. Malformed model decision
5. Duplicate action
6. Approval rejection

The system applies different recovery strategies depending on the failure.

# Phase 5 — Project 2: Customer Operations Agent

**Days 41–50**

Project 2 extends the validated LangGraph foundation into a business workflow.

## Day 41 — Business Workflow Design

The planned workflow is:

```text
customer_request
        ↓
identify_customer_and_order
        ↓
retrieve_operational_data
        ↓
retrieve_policy_evidence
        ↓
calculate_eligibility
        ↓
propose_action
        ↓
human_approval_interrupt
        ↓
execute_action
        ↓
audit_log
        ↓
communicate_result
```

The workflow state includes fields such as:

* `customer_tier`
* `policy_evidence`
* `eligible`
* `ineligibility_reason`
* `max_refund_amount`
* `proposed_action`
* `proposed_args`
* `user_role`

The eligibility engine is implemented as deterministic Python logic.

The architectural principle is:

> **The LLM explains and orchestrates; deterministic code makes business-rule decisions.**

# Development Philosophy

The journey is not organized around simply learning another framework.

Each phase attempts to answer an engineering question through implementation and measurement.

Examples:

* Does semantic retrieval actually improve this dataset?
* Which chunking strategy gives the best trade-off?
* Can citations be made structurally reliable?
* What happens when retrieval fails?
* Can an agent safely execute write operations?
* What happens when the same action is executed twice?
* What should the LLM decide?
* What should deterministic code decide?
* How should an agent recover from failure?
* How do we measure whether an agent is actually reliable?

The objective is to turn Generative AI from a demo into an **engineered system with measurable behavior**.
